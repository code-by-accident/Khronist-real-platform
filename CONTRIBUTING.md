# Як долучитися

Запуск проєкту, команди й типові проблеми описані в [docs/development.md](docs/development.md), влаштування системи — в [docs/architecture.md](docs/architecture.md), робота з продуктом — у [посібнику користувача](docs/user-guide.md). Історикам, які наповнюють довідковий корпус, потрібен [docs/corpus.md](docs/corpus.md).

## Шлях однієї зміни

```sh
git switch main
git pull
pnpm install
git switch -c feat/short-name
```

1. Одна задача — одна гілка. Назва англійською: `feat/...`, `fix/...`, `chore/...`, `docs/...`.
2. Коміти невеликі, повідомлення англійською за зразком `feat: add recognition endpoint`.
3. Запуште гілку й відкрийте PR у `main`. Шаблон PR підставиться сам.
4. Дочекайтесь зеленого CI й злийте PR.

`pnpm install` після кожного `git pull` обов'язковий: без нього нові залежності з `main` не встановляться, і код упаде на імпорті.

## Автоматичні перевірки

| Коли | Що запускається | Де |
| --- | --- | --- |
| перед комітом | `pnpm lint`, `pnpm typecheck`, `pnpm test`; якщо в коміті є файли `services/knowledge`, ще `uv run ruff check`, `ruff format --check`, `pytest` | локально, `.githooks/pre-commit` |
| перед пушем | заборона прямого пушу в `main` | локально, `.githooks/pre-push` |
| на кожному PR | те саме й `pnpm format:check`, `pnpm build`; міграції та запуск на справжньому PostgreSQL; перевірки `services/knowledge` | GitHub Actions, задачі `check`, `runtime` і `knowledge` |

Хуки вмикає `pnpm install`. Перевірка: `git config core.hooksPath` має вивести `.githooks`.

Прапорець `--no-verify` обходить хуки, але не CI. Не використовуйте його, щоб приховати падіння тестів.

У `main` діє ruleset GitHub: зміни лише через PR, злиття після зелених `check`, `runtime` і `knowledge`, без force-push і видалення гілки.

## Правила коду

- Код, імена й коміти англійською; інтерфейс, тексти для користувача, промпти й документація українською.
- Коментарів у коді немає. Пояснення виносьте в назви, типи й README теки.
- TypeScript у режимі `strict`, без `any`; Zod на межах системи. Python 3.12 з типами, ruff, Pydantic на межах.
- Контракти — Zod-схеми в `packages/contracts`. Зміна контракту — окремий PR, який погоджують власники обох боків.
- У `.ts` лише синтаксис, який стирається (без `enum`, `namespace`, параметрів-властивостей): Node запускає файли напряму, це перевіряє `erasableSyntaxOnly`.
- Дати в відповідях API повертаються рядком ISO: колонки Drizzle дають `Date`, перед серіалізацією викликайте `toISOString()`.
- Нічого не вигадуємо: ні фактів про архіви, ні джерел, ні назв моделей чи версій пакетів. Невідоме перевіряємо в документації або позначаємо `TODO(перевірити)`.
- В інтерфейсі лише чесні стани: немає функції — немає кнопки, невпевненість моделі видно, координати `estimated` малюються смугою, а не рамкою.
- Секрети лише через змінні середовища. Нова змінна одразу додається в `.env.example` і [docs/configuration.md](docs/configuration.md). Файл `.env` у git не потрапляє.
- Рішення про зміну обсягу й поведінки описуйте в PR.
- Зміни в чужій зоні (`services/*` і `packages/prompts` ведуть Анна і Катерина, `apps/*` — Владислав) описуйте в PR, а не робіть мовчки.
